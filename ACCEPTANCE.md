## Battery sysfs: детерминированные тесты и недоступные entries — АВТО, 23.09.2026
Причина прежней единственной unit-ошибки: `test_mvp.Commands.test_readonly`
вызывал проверку `BATTERY` на реальном `/sys/class/power_supply`. Traceback
показывает чтение `BAT1/capacity`; повтор подтвердил тот же `OSError: [Errno 19]`.

возвращает `ENODEV`. Это доказывает недоступность атрибута после обнаружения
entry, но по этому наблюдению нельзя заключить, исчез ли каталог именно в гонке

отдельный `OSError` при чтении type/capacity/status пропускает этот entry,
чтобы использовать следующую доступную Battery. Если sysfs нельзя перечислить
или ни одну обнаруженную батарею нельзя прочитать, возвращается понятный ответ
«Не удалось получить данные о заряде батареи.» Если Battery нет — «Батарея не
обнаружена.». Произвольные исключения не подавляются.

`BatteryTests` используют только временную папку и injected `OSError`/`PermissionError`:

## LOCAL queue: воспроизведение и исправление — АВТО, 23.09.2026
Сохранён весь WIP; резервная копия исходников до правок вне репозитория:

старым префиксом очереди и выполнение результата слишком долгого распознавания.
Все тесты используют виртуальные clocks/callbacks и искусственный PCM, без речи.

Причина на уровне кода: в ветке wake-speaking стоял Event.wait + continue без
чтения очереди. 12 блоков по 100 мс заполняются за 1,2 с даже без CPU starvation.
После перехода весь старый префикс проходил основной цикл по одному блоку;
свежий пользовательский PCM мог пересечь прежний лимит 400 мс, пока ждал очереди.

Временная диаграмма [детерминированного примера](logs/local-queue-timeline.log)
(PortAudio имеет отдельную эпоху +10000; здесь показаны относительные секунды):
```text
playback end          2,450
capture user block    2,510 ───────── 2,610 (100 мс)
callback / enqueue                    2,610
main observes exit                          2,750
queue: 10 старых блоков → user-first → user-second (depth=12, overflow=6)
раньше: старый префикс по одному → user-first устаревает до распознавания
теперь: один trim префикса → user-first с возрастом 240 мс → recognizer
```

Это воспроизведение алгоритмического дефекта, не измерение времени ноутбука.
Отдельный тест ожидания playback без задержки main раньше давал overflow=2;

по-прежнему возможен, но размер очереди не увеличен и старые команды не разрешены.

Исправление: consumer во время wake-TTS удаляет только уже просроченный префикс,
сохраняя свежий PCM независимо от того, успел ли main заметить playback exit.
При переходе одним проходом под mutex удаляются старые/TTS/пересекающие boundary
блоки до первого разрешённого. Следующие свежие блоки остаются в той же очереди,
с исходными timestamps и флагами разрывов. Callback, capacity=12, старые clock
boundaries и freshness=400 мс не изменены. Никакого grace window или иммунитета
от stale у сохранённых блоков нет. Просроченный результат распознавания также
сбрасывается до выполнения команды. Обычный TTS/retry cooldown сохранён.

Одна сводка `[LOCAL READY]` печатается после разбора сохранённых блоков либо выхода
из listening: boundary, poll_lag, исходная depth, overflow, expired_wait,
dropped, first_age/last_age на момент перехода, post_kept, post_stale,
stale_after, result_stale, unconsumed. `post_kept` — только блоки, уже стоявшие
в очереди на переходе; ноль не означает отсутствие дальнейшей речи. Сводка не
содержит PCM или распознанного текста и не печатается на каждом блоке.

### Process test: бюджет, стадия и неопределённость
Исторически ошибся один тест:
`test_bridge_shutdown.ShutdownTests.test_hung_job_kills_and_reaps_owned_tree_only`.
Две записи error относятся к нему и его cleanup: общий deadline истёк, затем

выхода supervisor после ACK о сборе потомков; ACK сам по себе недостаточен.
В историческом полном логе нет временных меток, поэтому распределение затрат
того запуска и конкретная причина задержки scheduler/exit **не установлены**.
Production race не воспроизведён и не объявляется исключённым для всех условий.

Расчёт существующего алгоритма при бюджете B: normal до 0,5B, TERM до 0,7B,
затем KILL/reap/IPC/выход supervisor/join controller должны уложиться в оставшиеся
0,3B; около конца есть резерв 0,1 с для сообщения об ошибке. При B=3 с kill начинается
около 2,1 с, хвост меньше 0,9 с. При production B=12 с — около 8,4 с и хвост меньше
3,6 с. Poll IPC — 20 мс, flush — до 10 мс за итерацию; длительного скрытого sleep
нет. Верхний предел успешного close — общий B, а не сумма новых таймаутов.
Не существует конечной гарантии задержки OS scheduling/непрерываемой D-задачи:
при исчерпании B cleanup остаётся неподтверждённым, LOCAL/new session запрещены.

## Второй LOCAL wake — диагностика и исправление, 24.09.2026

### Установленная причина: PRODUCTION reset lifecycle
Повторён простейший `local-clip-start-0` с `--debug-trace`, затем все шесть FAIL.
В исходной версии обёртка вызывала Vosk `Reset()`, но тот же wake backend
сохранял состояние, достаточное для повторного partial «михаил» после паузы.
Это ошибка достаточности reset в production использовании; не повтор WAV,
не FakeSpeech PCM и не доказанное слово «михаил» внутри записи времени.
Конкретная внутренняя структура Vosk, удерживающая состояние, не установлена.

Доказательство вне loop harness, на настоящем Vosk и той же grammar/model:
- свежий recognizer, исходные frames 54400..59199 из `local-time-01`: partial пустой;
- свежий recognizer на всём хвосте с frame 54400: «михаил» не возникает;
- прежние wake-входы + те же Reset + хвост: partial «михаил» появляется снова;
- тот же прежний recognizer, но вместо хвоста поданы нули: «михаил» снова появляется;
- замена экземпляра на reset устраняет повтор; полный command WAV с LOCAL grammar
  по-прежнему даёт «который час».
Логи: `logs/second-wake-isolated.log`, `logs/second-wake-context.log`.
В изоляции EOF FinalResult — только диагностика, не основание PASS.

`test_wake_reset_cannot_reuse_backend_feature_context_after_time` сначала
воспроизвёл FAIL `wake_count` при правильно выполненном TIME, затем прошёл.

Только LOCAL wake использует `FreshWakeRecognizer`: Reset отпускает прежний backend,
следующий допущенный PCM лениво создаёт новый с прежней Model и grammar. Model

stale/playback/cooldown, thresholds и browser-код в этом проходе не менялись.
В `audio_replay.py` узко адаптировано чтение прежней wake grammar из AST к явному

capture/delivery/queue, instance/reset IDs, partial/final, state transitions и
окончание сценария. В trace нет PCM/локальных переменных/переписки GPT.

пакета recognizer последним реальным dequeued блокам, включая preroll.
Обычный production logging не расширен; trace не включается без флага.

Постоянные invariants запрещают duplicate capture delivery и пересечение уже
доставленных source ranges внутри одного объявленного step/clip/block.

аналог — новые последующие capture-блоки; endpoint не отменяет физический timeline.

lifecycle, не синтезирует свой текст в PCM.

### FreshWake: read-only review и инструментация
Первый backend создаётся при инициализации listen до запуска stream/приветствия;
он отпускается первым Reset. Далее Reset делает `rec=None` и отпускает старый
backend. Новый появляется лениво на первом допущенном PCM; повторные Reset без
PCM ничего не создают. Обычно один backend на допущенный wake-отрезок, плюс
первоначальный экземпляр за запуск; строгого числа «на цикл» нет: gap/stale и
новый RMS-отрезок после истечения tail также сбрасывают wake. В детерминированном
одном цикле без нового шума — два создания вместе с первоначальным.

Factory держит одну общую Model/grammar, а не прежний backend. Локальная `rec`
в listen ссылается на wrapper, не на освобождённый backend. В установленном Vosk
`KaldiRecognizer.__del__` вызывает `vosk_recognizer_free`. Weakref-тест подтвердил
освобождение backend/model refs и отсутствие удержания instrumentation; это
проверка Python lifetime, не длительный native-memory soak. Утечка не доказана.
Конструктор/Accept идут в main thread, не в callback. Во время playback/cooldown
recognition path не допускается; callback только кладёт PCM. Создание способно
задержать main loop и конкурировать за CPU — фактическая live стоимость ещё
не принята. Начальное лишнее создание оставлено, speculative optimization нет.

`wake_perf.py` — отдельный opt-in инструмент. Без `--live` только offline Vosk;
с `--live` временно оборачивает FreshWake factory и вызывает обычный `main.main()`
с прежними cleanup/SIGINT semantics. По умолчанию приложение его не использует.
Измеряются create/первый Accept/generation, mean/max/count; нет PCM/речи в метриках.
Хранятся максимум 1000 числовых записей, mean/max/count за весь запуск. Модель
не перезагружается, backend refs статистика не удерживает. Обычные LOCAL ASR logs
приложения при live-launcher сохраняются отдельно от этих метрик.
