# Повседневный запуск — проект, не установленная служба

25.09.2026. Выполнять после live regression и измерений из
[backlog](PERFORMANCE-BACKLOG.md). Сейчас systemd/autostart не добавляются,
пакеты, пользовательская сессия и audio defaults не изменяются.

## Предлагаемая организация

- Один процесс Михаила на пользователя: отдельная runtime-lock с удерживаемым
  файловым дескриптором на всё время жизни. PID-файл сам по себе не lock.
  Повторный запуск сообщает «уже запущен» без запуска нового browser worker.
- User-level service, без root; запуск только после готовности пользовательской
  графической и PipeWire сессии. Привязку к фактическому session target Lubuntu
  и передачу DISPLAY/XAUTHORITY/DBUS/XDG_RUNTIME_DIR проверить на этой машине
  перед реализацией. Не угадывать значения и не хранить их в repo.
- `ExecStart` будущего unit использует существующую .venv и рабочий каталог;
  не pipeline через tee. При необходимости отдельное автозапуск-событие desktop
  лишь запускает user service, не второй Python. Boot без graphical login не
  должен запускать Firefox в неподходящей среде.
- Проверка readiness локальная: модель, аудио-session, Speech ready; короткое
  звуковое уведомление после фактической готовности, не при одном старте Python.
  Недоступный профиль/устройство — понятный ограниченный отказ, не busy loop.
- Ограниченный restart-on-failure с паузой и лимитом попыток. Намеренная остановка
  не рестартуется; неправильный config и неподтверждённый browser cleanup не
  запускают бесконечную серию новых сеансов.

## Shutdown и владение

Обычная остановка должна проходить существующий application cleanup вне signal
handler. Перед реализацией проверить обработку service stop signal отдельно от
уже проверенного SIGINT/PTY. Общий browser budget остаётся 12 с; будущий service
stop budget включает также Speech/monitor и supervisor reaping с измеренным
запасом. Значение не выбирать меньше суммы этих ограниченных этапов.

Не полагаться на один `KillMode=control-group` как на доказательство безопасности:
LOCAL-команда открытия обычного Firefox способна запустить пользовательский
браузер из того же service context. `setsid()` browser supervisor не доказывает
выход из cgroup. До включения службы проверить фактическое дерево/cgroup,
долговременное владение и политику запуска не принадлежащих GPT приложений.
Автоматический fallback не должен закрывать чужой Firefox.

Persistent GPT profile используется одним подтверждённым владельцем. Новый
worker только после подтверждённой очистки старого; profile/lock-файлы не удалять
для обхода работающего процесса. После reboot сначала проверить новое session
окружение и владение, затем открыть профиль штатно. «Нет PID» не заменяет
проверку идентичности/состояния процесса.

## Health и logs

Health metadata: process/session generation, mode/phase, возраст последнего tick,
guard available, pending job/cleanup state; без PCM/разговора. Readiness не равно
«ответ ChatGPT доступен». До выбора heartbeat/watchdog получить baseline
допустимых startup/main-loop задержек; не убивать нормальный медленный startup.

Logs локальны, с ограничением размера/срока и правами пользователя. Существующий
LOCAL ASR может содержать пользовательскую команду: не публиковать logs и не
превращать их в историю памяти. Выбор journal/rotation — будущая настройка;
BrokenPipe/logger failure по-прежнему не должны отменять cleanup.

## Условия внедрения

Сначала отдельные tests single-instance, restart limit, deliberate stop, session
unavailable, cleanup failure и отсутствие чужих жертв; затем ручной вход/выход
из graphical session и reboot по отдельному разрешению. Нужны измерения RSS/CPU,
обычный длительный прогон и голосовой путь остановки. Ничего не устанавливать
до прохождения этих условий. Unit template будет отдельной реализацией, не
следствием чтения этого design.
